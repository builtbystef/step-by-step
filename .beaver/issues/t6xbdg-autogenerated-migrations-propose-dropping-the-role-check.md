## What is wrong

Every `alembic revision --autogenerate` run after the accounts schema proposes two changes nobody asked for:

```
op.drop_constraint(op.f('invitation_role'), 'invitations', type_='check')
op.drop_constraint(op.f('membership_role'), 'memberships', type_='check')
```

SQLAlchemy's non-native `Enum` (`accounts/models.py`'s `role_column`, `native_enum=False, create_constraint=True`) writes those check constraints into the database but does not present them to autogenerate's comparison, so the reflected constraint looks like one the metadata dropped. It first showed up while generating the Workflow document store migration (`sl7h4j`), where the two lines were deleted by hand.

Left alone this is a live foot-gun: a revision generated in a hurry and applied unread silently removes the constraint that keeps a Membership's role one of owner/admin/member.

## Acceptance criteria

- [ ] Autogenerating a revision against a database at head, with no model changes, produces an empty `upgrade()` — no proposed constraint drops.
- [ ] The role check constraints still exist in the database after a fresh `alembic upgrade head`, and inserting a Membership with a role outside the three is still refused.
- [ ] The architecture doc's migration paragraph loses the quirk note it currently carries.

## Notes

The usual fix is an `include_object` hook in `alembic/env.py` that skips check constraints alembic cannot see in the metadata; whatever the shape, it must not blind autogenerate to constraints a future model really does remove.
